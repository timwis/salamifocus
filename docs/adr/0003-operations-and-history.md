# Operations, identity and history

Ticket 03 needs to define identity, attribution, exactly-once application and original-capture storage on the application-owned write path established by ADR 0001. Propose client-generated UUIDs and named logical operations, applied through a single application boundary that validates mutations and records their attributed history atomically, with actors derived from authenticated sessions. This keeps retries from duplicating changes, prevents agents from labelling themselves as the user, and lets history and the future agent API share the same write path.

## Consequences

1. **Identity.** Every row's id is a UUID chosen by the client that creates it, at the moment it is created, including offline. The server never reassigns ids.

2. **Operations.** Every change is a named logical operation (`capture_text`, `rename_task`; names in `domain/src/operations.ts`) with an operation id, a UUID generated by the client for that one action. The client writes the operation's rows in one local transaction and tags each row with `_metadata = {"op_id": …, "op": …}`.

3. **Actor.** The actor is never taken from the client's metadata. The server derives it from the authenticated session: currently always the single user, `{type: "user", id: "owner"}`, with the session's client label (for example `android` or `web`) recorded as the source. This keeps the spec's rule that an agent cannot become the user by labelling itself. It differs from ADR 0001, which put the actor in `_metadata`.

4. **Write path.** `POST /api/sync/upload` receives one client transaction. The server regroups the rows by `op_id`, checks they have the shape their operation allows (for example, a rename may change only `title`), and hands each operation to the application's `execute`. In one Postgres transaction, `execute`:
   - takes an advisory lock on the operation id and returns the recorded outcome if the id has been seen before (a retry after a lost acknowledgement), counting the extra delivery;
   - validates and applies the operation;
   - writes the `operations` row (name, actor, source, outcome, and what was submitted) and one `changes` row per row created, updated or deleted, with before and after values.

   Mutations go through a single recorder (`server/src/application/mutations.ts`), so an operation cannot change state without producing change records.

5. **Rejections.** A business-rule refusal (blank title, unknown task, malformed rows, unknown operation) is recorded with its reason and the submitted rows, and acknowledged with 200. Sync then reverts the client's optimistic write. Only faults (for example, the database being unavailable) return an error status, so the client retries them. A server bug therefore stalls a client's queue until it is fixed, rather than losing its writes.

6. **Original capture.** `captures` holds the text exactly as typed and is never updated. The task's title starts as the trimmed capture text and is changed only by operations on the task.

7. **Authentication.** One owner password, configured as a scrypt hash in `OWNER_PASSWORD_HASH`. Signing in creates a revocable session (an opaque bearer token stored hashed). With a session, a client fetches 10-minute PowerSync tokens signed with an Ed25519 key, whose public half is published at `/.well-known/jwks.json` for the PowerSync service.

8. **One address per server.** The app server proxies `/powersync/*` to the PowerSync service, so each client needs only the server's base URL. Clients therefore use PowerSync's HTTP streaming connection, not WebSockets.

9. **Application boundary.** The application's public surface is `execute(operation)` plus queries (`inbox`, `task`, `history`, `operation`) in `server/src/application/`. The sync endpoint is one adapter onto it. The agent API (ticket 26) is meant to be another. The test harness drives this boundary directly against a real Postgres.

- History (ticket 06) can be read from `operations` and `changes` without new write-side work. One logical operation is one entry, however many times it was delivered.
- Change records are not synced to clients yet. Rejections are visible only on the server for now. Surfacing them, and detecting same-field conflicts from the previous values clients already send (`trackPrevious`), is ticket 34.
- Records are not deleted, with one exception (ticket 08): taking a tag off a task deletes its link row in `task_tags`. A plain SQL `DELETE` carries no metadata, so the client writes `UPDATE task_tags SET _deleted = TRUE, _metadata = …`, which PowerSync uploads as a `DELETE` tagged with its operation. The change is recorded with kind `delete`, the removed row as `before` and no `after`. Ticket 18 should still mark tasks, projects and other records deleted rather than delete them.
- The sign-in endpoint delays failed attempts but has no lockout. Ticket 04 should add rate limiting before the server is exposed to the internet.
